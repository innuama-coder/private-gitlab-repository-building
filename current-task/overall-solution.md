# 总体方案

## 01. 方案结论

采用“家庭主节点 + 云端公网入口”的双节点方案：主服务放在家庭网络中的高性能设备，公网访问放在具备固定公网地址的云主机；两者通过加密私网连接。

## 02. 节点职责

### 主节点

- 运行代码托管服务、CI/CD 服务和主要 Runner。
- 保存仓库、流水线制品和服务配置。
- 保持接电、联网和自动恢复。

### 公网入口节点

- 接收域名的 HTTPS 和 Git SSH 请求。
- 终止 HTTPS 或转发加密流量。
- 通过私网连接把请求转发到主节点。
- 不保存核心仓库数据。

### 备用节点

- 首期不承载生产请求。
- 后续用于备份、第二个 Runner 或入口节点故障切换。

## 03. 网络路径

```text
外部用户
  -> 公网域名
  -> 公网入口节点
  -> Tailscale 私网
  -> 主节点上的 GitLab
```

## 04. 服务组成

- GitLab：代码、权限、Issue、Merge Request 和 CI/CD 编排。
- GitLab Runner：执行测试、构建和发布任务。
- Caddy 或 Nginx：提供公网 HTTPS 入口和反向代理。
- Tailscale：提供主节点与公网入口节点之间的私网连接。
- 独立备份目标：保存可恢复的 GitLab 备份。

## 05. 访问策略

- Web 访问使用 HTTPS 域名。
- Git 访问同时支持 HTTPS 和标准 SSH。
- 主节点不直接开放公网端口。
- 管理入口启用强密码、双因素认证和最小权限。
- 公网入口只开放必要端口，管理 SSH 限制来源。

## 06. 数据策略

- 仓库和 GitLab 数据保存在主节点的独立数据目录。
- 每日执行备份，保留多个历史版本。
- 至少保留一份与主节点不同位置的备份。
- 定期进行恢复演练，确认备份不仅存在，而且可用。

## 07. 取舍

- 选择单节点 GitLab，换取更低的初始运维复杂度。
- 选择家庭主节点，换取更充足的 CPU、内存和磁盘资源。
- 选择云端公网入口，换取稳定的外部访问能力。
- 暂不建设高可用集群，等使用量和故障数据证明需要后再升级。
